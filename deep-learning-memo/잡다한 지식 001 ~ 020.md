HTTP 헤더와 바디

바디(body): 택배 상자 안의 내용물
진짜 보내고싶은 데이터

헤더(header): 택배 상자에 붙은 운송장
내용물을 안전하고 정확하게 보내기 위해 필요한 부가 정보(메타데이터)

그럼 바디에 이미지 바이너리 데이터와 객체탐지 정보를 다 보내면 안되냐?
물론 그래도 됨
1. 하지만 바디에 다 넣으려면 속도 저하가 발생한다.
json은 텍스트 포맷이기 때문에 순수 바이너리 데이터를 넣을 수 없다.
그래서 이미지를 문자열로 바꾸는 base64 로 변환 과정을 거쳐야 한다.
그런데 base64로 인코딩하는 과정에서 데이터 크기가 약 33% 정도 증가한다. 그러면 네트워크 전송 속도도 느려진다.
그리고 CPU 연산 낭비.. 파이썬 서버에서 인코딩하고, 자바에서 다시 디코딩하는 불필요한 연산이 발생한다.

2. HTTP 표준 프로토콜의 목적에 맞기 때문이다.
HTTP 프로토콜은 "바디에는 알맹이 데이터 딱 하나만 넣는 것"을 기본으로 설계되었다.

로드 밸런싱

로드 밸런싱은 네트워크 또는 서버에 가해지는 부하 트래픽을 분산시켜주는 기술입니다.
두 가지 방법이 있습니다. Scale up, Scale out

(1) Scale-up의 경우 서버의 자체 사양을 높이는 것을 말합니다.
하드웨어적으로 서버에 디스크를 추가하거나 CPU, RAM 자원을 업그레이드하는 방식입니다.

장점: 
ㅇ 추가적인 네트워크 연결 없이 서버의 자원을 늘릴 수 있습니다.
ㅇ Scale out 방식보다 관리 비용이나 운영 이슈가 적고 확장 방식이 비교적 간단합니다.

단점: 
ㅇ 하드웨어 비용부담이 크고 업그레이드 범위가 정해져 있어서 성능 향상에 한계가 있습니다.
ㅇ 만약 서버 한 대가 모든 부하를 감당해야 하고 그 서버가 터진다면 서비스 장애가 발생할 수 있습니다.


(2) Scale out의 경우 서버의 개수를 늘리는 것입니다.

비슷한 사양의 서버를 추가로 연결해 트래픽을 분산시키는 것입니다.

장점: 
ㅇ 유연한 확장성을 가집니다.
ㅇ 서버 한 대가 다운되더라도 나머지 서버로 서비스를 운영할 수 있습니다.
ㅇ 필요한 만큼 서버를 증설할 수 있어서 제한이 없습니다.

단점: 
ㅇ 병렬 컴퓨팅 환경을 구성해야 하기 때문에 관련 아키텍처에 대한 높은 이해도가 필요합니다.
ㅇ 여러 서버가 존재하기 때문에 데이터 일관성이 깨질 수 있습니다. (아키텍처 설계 과정이 중요)
ㅇ 여러 서버에 균등하게 부하를 분산시키기 위해 로드 밸런서가 필요합니다.


로드 밸런서는 인터넷과 서버 사이에 있다.
정상적으로 운영되고 있는 서버에게만 요청을 전송.
