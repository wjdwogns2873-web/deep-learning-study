MVC 패턴

ㅇ Model
	ㅇ 비즈니스 로직 및 데이터 담당
	ㅇ DB에서 가져온 DTO나 서비스 레이어(@Service)에서 처리된 결과물
ㅇ View
	ㅇ 사용자에게 보여줄 화면
ㅇ Controller
	ㅇ 중재자 역할
	ㅇ 클라이언트의 HTTP 요청을 가장 먼저 받아서 필요한 서비스(Model)을 호출하고, 그 결과를 어떤 화면이나 데이터로 응답할지 결정한다.

스프링 부트로 만든 웹 서버로 HTTP 요청이 들어오면 아래 순서대로 동작한다.

0. 클라이언트 요청
1. DispatcherServlet (모든 HTTP 요청을 한곳에서 모아 받음)
2. HandlerMapping (요청 URL과 HTTP 메서드에 맞는 @Controller 메서드 찾음)
3. Controller (비즈니스 로직 실행 후 결과 Model 데이터 생성)


Spring MVC는 HTTP 요청을 효율적으로 받아서 처리하기 위해 Model, View, Controller 역할로 구조화한 스프링의 웹 프레임워크 모듈이며, @RestController나 @GetMapping 등을 통해 웹 요청 처리를 자동화해 주는 핵심 라이브러리.

쇼핑 장바구니에 물건을 추가하는 로직을 생각해본다면,

사용자가 view(화면)에서 장바구니 추가 라는 요청을 하면 controller는 그 요청에 해당하는 http 요청을 찾아서 Model을 실행하고, 그 실행 결과를 사용자 화면에 다시 보여준다.

REST(REpresentational State Transfer)

ByteArrayResource 객체를 생성할 때 getFilename()을 오버라이딩하는 이유?

ByteArrayResource의 한계: 파일 이름이 없다.

자바의 ByteArrayResource는 메모리 상의 바이트 배열(byte[])을 외부로 전송하기 위해 포장해주는 클래스입니다. 하지만 이 녀석은 "이름이 없는 파일"입니다.

파이썬의 UploadFile은 HTTP 요청 데이터에서 파일명이 제대로 들어왔는지를 확인합니다.
만약 자바에서 getFilename()을 정의하지 않고 파이썬으로 넘겨버리면 HTTP 요청 메시지에 파일명이 null로 찍힙니다.
그렇게 되면 파이썬에서 에러를 발생시킵니다.

중괄호의 정체: 익명 클래스 (Anonymous Class)
자바에서는 기존 클래스의 일부 메서드만 오버라이딩해서 쓰고싶을 때, 클래스 파일을 새로 만드는 대신 코드 가운데에 일회용으로 클래스를 재정의할 수 있다.

동영상을 바이트(file.getBytes())가 아닌 file.Resource()로 보내는 이유:
대용량 메모리 낭비(Out Of Memory)를 방지하기 위해

이미지 vs 동영상
ㅇ 이미지는 동영상에 비해 크기가 매우 작습니다. 그래서 메모리에 file.getBytes()로 올려도 큰 부담이 없습니다.
ㅇ 동영상은 용량이 매우 큽니다. file.getBytes()를 쓰면 메모리에 다 올리면 메모리가 꽉 차서 다 올릴 수가 없습니다. OutOfMemoryError 뜰 가능성이 있습니다.

file.getResource()의 동작 방식:
동영상 전체 데이터를 메모리에 다 올려두는 것이 아니라, 데이터가 흘러갈 수 있는 '통로 정보만 가진 객체'를 전달합니다.
ㅇ 메모리 절약: RestTemplate이 파이썬 서버로 데이터를 전송할 때, 동영상 통째로 올려서 보내는 게 아닌, 스트림(통로)을 통해 데이터를 조금씩 쪼개서(Streaming) 전달합니다.
ㅇ 파일명 유지: ByteArrayResource와 달리, file.getResource()는 파일명(getFilename())도 가지고 있어서 오버라이딩 없이 파이썬 서버가 파일명을 정상적으로 인식할 수 있습니다.
